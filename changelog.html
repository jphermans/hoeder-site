Hoeder A vault for the few things that must survive you.

Version history

What changed, in the order it changed. The version you are holding is in the app under Settings › About, which shows the current list; this page keeps all of it.

1.1.6 — build 8

A four-digit PIN, if that is what you want.

The PIN can be four digits as well as six, chosen during setup. Four digits means ten thousand possibilities instead of a million, so the app does what can honestly be done about it: a four-digit vault derives its key eight times more slowly — and the cost is stored with the vault, so it stays right — while the screen where you choose says what the trade is instead of quietly letting you pick the weaker door.

Every PIN pad sizes itself to the length the vault was made with. A four-digit vault drawn on a six-digit pad would be a vault nobody can open, so a test asserts it screen by screen.

1.1.5 — build 7

About has its own tab.

It was a row inside Settings, in a card next to Pro, the guide and the privacy policy — three neighbours with nothing to do with it. The version, what changed, where your data lives and who made it are now one tap away under a large title of their own, and the Settings row is gone so there is exactly one way in. A test asserts that: the tab is declared, the old screen no longer exists, and nothing links to it.

1.1.4 — build 6

The maker's name on the splash screen.

JPHsystems fades in under the tagline as the third and quietest beat, so the first thing the app shows is who made it. The name lives in one place in the code and is the same one Settings → About and the terms of use use. It is part of the JavaScript splash rather than the launch image, because that image is a single bitmap scaled to a fixed width — text baked into it would shrink the seal and produce a visible jump at handover.

1.1.3 — build 5

Export and import say what happened, and export checks its own work.

It speaks up now

A passphrase that was too short, or typed differently in the second field, was reported as a small caption underneath a card. Tapping Export and seeing nothing happen read as "the export is broken" — while the export had simply stopped. Both cases now raise a message, and so does the outcome: the file name, its size and where it lives; or the exact reason it failed.

Export checks its own work

After writing, the app reads the file back and refuses to report success if nothing — or an empty file — landed, because an export that silently wrote nothing is the worst kind: the user then believes they have a backup.

1.1.2 — build 4

A missing file says so, and a reinstall can no longer blank a picture.

A missing photograph says so

The photo area was an image with no error handling, so a file that could not be loaded left an empty rectangle while the anchor and its "remove photo" control were still on screen. It now states that the file is not on this device, and that the anchor and its details are intact.

Paths are resolved, not trusted

Stored media paths are absolute, and iOS gives an app a new container identifier on reinstall — an old path then looks valid while pointing somewhere that no longer exists. The part that matters is kept and the root rebuilt against the container in use.

A media inventory at every launch

The app checks that the files its database promises actually exist, counts files that no row refers to, records the answer, and deletes the unreferenced ones: deleting a photograph has to mean the bytes are gone.

1.1.1 — build 3

One file, one extension, and a backup a new phone can open.

One file instead of two

Export used to write two artefacts — one of them a .zip holding base64 text under a .zip name, which could never be imported — and nothing said which one was the real backup. There is now exactly one: hoeder-vault-<date>.hoeder.

A passphrase, so a backup survives a lost phone

The file was sealed with the vault key, which is random and lives in this device's keychain — so an export could only ever be opened on the device that wrote it, which is exactly not the situation a backup is for. It is now sealed with a passphrase you choose, with the salt and cost stored inside the file, so it opens anywhere.

Import that says what is wrong

One message used to cover a wrong passphrase, a foreign file, a damaged archive and an unreadable one. Each has its own sentence now, in three languages.

Proven, not assumed

A test builds a vault with two anchors — one holding a photograph and a twelve-second voice note — seals it through the real file format, opens it again and checks every record (type, title, why, care, handoff), that both media are still attached to their anchor with the right kind and duration, and that the bytes sit under the entry each record names.

1.1 — build 2

The first version prepared for the App Store and Google Play.

Your vault is no longer in the folder iOS shares

The database and the photographs used to sit in Documents, which is the one folder an app can expose to the Files app — and it exposes all of it. Photographs and voice notes are not encrypted, so that would have made them readable without the PIN. They now live in the app's private directory, and only exported backups stay behind in Files → On My iPhone → Hoeder → Backups, which is what makes them findable in the first place. Existing vaults move on first launch: files first, then the paths in the database that point at them.

About

Settings › About is now a real screen: the version and build taken from the app itself rather than a constant, what changed, where your data is, and links to this page and to support.

Android

  • The lock screen always sets FLAG_SECURE, so the PIN pad cannot appear in a screenshot or in the task switcher, whatever the user's screenshot setting says.
  • The screen-overlay permission is stripped at build time: nothing to draw over other apps, and one fewer policy declaration.
  • Root, jailbreak and emulator state are read and reported in Settings › Security — with the honest caveat, in three languages, that anchor text stays encrypted while photographs and voice notes do not. It never blocks the app: anything rooted can hide from the check, and the protection is the encryption, not a boolean.

Unlocking

Deriving the vault key from the PIN was a single synchronous 120 000-iteration PBKDF2 loop, measured at 8.6 seconds on the device, because the JavaScript engine on device has no JIT. It now runs in the operating system's crypto and takes about 30 ms, with the iteration count unchanged and the derived bytes verified identical — the key is part of the vault format, so a one-byte difference would have made existing vaults unreadable.

Appearance

A real dark appearance (warm charcoal, never pure black) with three states in Settings: Automatic, Light, Dark. A test computes the WCAG contrast of every text pair in both palettes, which caught a caption colour at 3.31:1 — below the 4.5:1 minimum — now 4.76:1.

Splash

A launch screen that hands over to the app without the mark jumping size, held 1.4 s on a first run and 0.65 s afterwards, so the app does not appear to start reluctantly.

Demo content

Five anchors, one of each type, in the language you chose, with drawn rather than stock photographs: enough for a reviewer to see a populated vault in about a minute. Every demo anchor is a real anchor in the encrypted vault, and removing them can only ever touch the ids the app recorded when it created them.

1.0 — build 1

Internal build. Never distributed.

The vault itself: a six-digit PIN, a randomised AES-256-GCM vault key wrapped by a PBKDF2-derived key and held in the system keychain, optional biometric unlock, five anchor types with three layers each (now, care, handoff), photographs and 20-second voice notes, the Year Ring, export and import, a second steward, and Dutch, French and English throughout.
